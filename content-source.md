## Цель

Убедиться, что на компьютере установлено всё необходимое для работы: терминал, Git и Node.js. Если чего-то нет — установить.

## Инструкция (пошагово)

1. Откройте терминал:
   - **Windows:** PowerShell (Пуск → введите «PowerShell»)
   - **macOS:** Terminal (Cmd+Space → «Terminal»)
   - **Linux:** любой привычный терминал
2. Проверьте Git:
   ```bash
   git --version
   ```
   Нет? Установите с git-scm.com (Windows/macOS) или через пакетный менеджер (`sudo apt install git` и т.п.).
3. Проверьте Node.js (нужна версия 18 или новее):
   ```bash
   node --version
   ```
   Нет или версия ниже 18? Установите LTS-версию с nodejs.org.
4. Проверьте npm (ставится вместе с Node.js):
   ```bash
   npm --version
   ```
5. После любых установок **закройте и заново откройте терминал**, затем повторите проверки.

## Критерий выполнения

Задача выполнена, если все три команды (`git --version`, `node --version`, `npm --version`) выводят номера версий, и версия Node.js — 18 или выше.

## Подсказки

- **Команда установлена, но «не найдена»** — почти всегда лечится перезапуском терминала. Установщики добавляют программы в системный путь, но открытые окна терминала об этом не знают.
- **Не знаете, что выбрать на сайте Node.js** — берите зелёную кнопку LTS, это стабильная версия.
- **Нет прав на установку (рабочий компьютер лаборатории)** — обратитесь к администратору.

## Цель

Установить Claude Code на свой компьютер и убедиться, что он готов к работе.

## Инструкция (пошагово)

1. Убедитесь, что выполнена задача 01-00 «Подготовка окружения» (Node.js 18+ и npm работают).
2. Установите Claude Code глобально через npm:
   ```bash
   npm install -g @anthropic-ai/claude-code
   ```
3. Закройте терминал и откройте заново.
4. Проверьте установку:
   ```bash
   claude --version
   ```

## Критерий выполнения

Задача выполнена, если команда `claude --version` выводит номер версии без ошибок.

## Подсказки

- **«command not found» / «не является командой» после установки** — сначала просто перезапустите терминал. Не помогло — смотрите следующую подсказку.
- **Windows: `'claude' is not recognized…` даже после перезапуска.** Папка глобальных npm-пакетов не попала в переменную `Path`. Решение:
  1. Узнайте правильный путь: выполните `npm config get prefix` — например, `C:\Users\ИмяПользователя\AppData\Roaming\npm`.
  2. Нажмите `Win + R`, введите `rundll32 sysdm.cpl,EditEnvironmentVariables` и нажмите Enter.
  3. В блоке «Переменные среды пользователя» выберите `Path` → «Изменить» → «Создать» → вставьте путь из шага 1 → «ОК» во всех окнах.
  4. Откройте новый терминал и повторите `claude --version`.
- **Ошибка прав доступа (EACCES) при `npm install -g` (macOS/Linux)** — не запускайте через `sudo`; настройте npm-префикс в домашней папке или используйте nvm.

## Цель

Авторизоваться и провести первый диалог с Claude Code.

## Инструкция (пошагово)

1. Создайте пустую папку для экспериментов и перейдите в неё:
   ```bash
   mkdir claude-sandbox && cd claude-sandbox
   ```
2. Запустите Claude Code:
   ```bash
   claude
   ```
3. При первом запуске откроется авторизация — войдите через аккаунт Claude (подписка) или Claude Console (API). Следуйте подсказкам в браузере.
4. Вернувшись в терминал, дождитесь приглашения к вводу.
5. Отправьте первое сообщение, например: «Привет! Расскажи коротко, что ты умеешь».
6. Прочитайте ответ. Выйти из сессии можно командой `/exit` или сочетанием Ctrl+C (дважды).

## Критерий выполнения

Задача выполнена, если вы отправили сообщение, получили ответ и вышли из сессии.

## Подсказки

- Если браузер не открылся автоматически, скопируйте ссылку из терминала вручную.
- Каких-либо файлов на этом шаге не создаётся — это просто разговор. Работа с проектом начнётся в следующей задаче.
- Тип аккаунта (подписка или API) уточните у автора курса — в лаборатории используется единый способ входа.

## Цель

Понять, что Claude Code видит файлы проекта, в котором запущен, и умеет отвечать на вопросы о них.

## Инструкция (пошагово)

1. Выберите папку с любым реальным проектом (рабочим или учебным). Если под рукой нет — склонируйте любой небольшой открытый репозиторий с GitHub.
2. Перейдите в папку проекта и запустите `claude`.
3. Попросите описать проект, например: «Опиши структуру этого проекта: что это, из чего состоит, где точка входа».
4. Задайте уточняющий вопрос про конкретный файл, например: «Что делает файл package.json?» (или любой файл вашего проекта).
5. Обратите внимание: чтобы ответить, Claude сам читает файлы — вы увидите это в выводе.

## Критерий выполнения

Задача выполнена, если Claude перечислил реальные файлы/папки вашего проекта и ответил на вопрос об одном конкретном файле.

## Подсказки

- Claude Code работает в пределах папки, где запущен. Запускайте его в корне проекта, а не в домашней директории.
- Если проект большой и ответ кажется поверхностным — попросите сузить: «Разбери только папку src».
- На этом шаге ничего менять не нужно — только вопросы. Первую правку сделаем в задаче 01-06.

## Цель

Научиться пользоваться встроенной справкой и понять, что команды, начинающиеся с `/`, управляют самой сессией, а не отправляются модели как текст.

## Инструкция (пошагово)

1. Запустите `claude` в любой папке.
2. Введите `/` и посмотрите: появится список команд с автодополнением.
3. Введите `/help` и нажмите Enter.
4. Пролистайте список доступных команд. Найдите три команды, о которых в этом модуле речи не будет, и прочитайте их краткие описания.
5. Обратите внимание на подсказки по горячим клавишам, если они показаны.

## Критерий выполнения

Задача выполнена, если вы можете назвать три команды из справки, не входящие в этот модуль, и одним предложением сказать, что делает каждая.

## Подсказки

- Список команд зависит от версии Claude Code и может отличаться от чужих скриншотов — это нормально.
- Автодополнение по `/` работает как фильтр: начните печатать название, список сузится.

## Цель

Освоить самый безопасный режим работы: задавать вопросы о коде, ничего в нём не меняя.

## Инструкция (пошагово)

1. Запустите `claude` в папке проекта (можно тот же, что в задаче 01-03).
2. Задайте 3–4 вопроса о коде, например:
   - «Что делает функция X в файле Y?»
   - «Где в проекте обрабатываются ошибки?»
   - «Есть ли в этом коде очевидные проблемы? Только перечисли, ничего не исправляй.»
3. Обратите внимание на формулировку последнего вопроса: явное «ничего не исправляй» — полезная привычка, когда нужен только анализ.
4. Проверьте (например, через `git status`), что файлы не изменились.

## Критерий выполнения

Задача выполнена, если вы получили ответы минимум на три вопроса о коде, и `git status` (или ручная проверка) показывает, что файлы не менялись.

## Подсказки

- Чем конкретнее вопрос, тем полезнее ответ: «почему медленно работает поиск в utils.js» лучше, чем «посмотри код».
- Если Claude предлагает сразу что-то исправить — просто откажитесь или напомните, что сейчас нужен только анализ.

## Цель

Сделать первую правку через Claude Code и понять механизм подтверждения: Claude показывает diff и ждёт вашего разрешения.

## Инструкция (пошагово)

1. Работайте в учебном проекте или на отдельной ветке — не в важном коде.
2. Попросите маленькую правку, например: «Добавь поясняющий комментарий к функции X» или «Переименуй переменную a в userCount в файле Y».
3. Когда Claude предложит изменение, **не подтверждайте сразу** — прочитайте diff: зелёные строки добавляются, красные удаляются.
4. Подтвердите изменение.
5. Откройте файл в редакторе и убедитесь, что правка на месте.
6. Посмотрите варианты ответа на запрос разрешения: обычно можно разрешить один раз, разрешить на всю сессию или отклонить.

## Критерий выполнения

Задача выполнена, если правка применена, и вы видели diff до подтверждения и файл после.

## Подсказки

- Правило курса: **сначала читать diff, потом подтверждать.** Привычка «жать да не глядя» — главный источник проблем у новичков.
- Если diff не тот, что вы хотели, — отклоните и переформулируйте запрос точнее.

## Цель

Научиться останавливать Claude на полпути и корректировать курс — это нормальная часть работы, а не аварийная кнопка.

## Цель

Понять, что такое контекст сессии, чем очистка отличается от сжатия и когда применять каждую команду.

## Инструкция (пошагово)

1. Проведите короткий диалог из 3–4 сообщений на одну тему (например, обсудите структуру проекта).
2. Выполните `/compact`. Claude сожмёт историю разговора в краткое резюме, сохранив суть.
3. Задайте вопрос, опирающийся на предыдущее обсуждение, — убедитесь, что Claude помнит суть.
4. Теперь выполните `/clear` — история очищается полностью.
5. Задайте тот же вопрос с отсылкой к прошлому («как мы обсуждали выше…») — убедитесь, что Claude больше не знает, о чём речь.

## Критерий выполнения

Задача выполнена, если вы применили обе команды и можете своими словами объяснить разницу: когда достаточно сжать, а когда лучше начать с чистого листа.

## Подсказки

- Практическое правило: `/compact` — когда продолжаете ту же задачу, а контекст разросся; `/clear` — когда переходите к новой, не связанной задаче.
- Контекст ограничен, и чем он замусореннее, тем хуже ответы. Управление контекстом — один из главных навыков работы с Claude Code.

## Цель

Научиться отменять правки, сделанные через Claude Code, — чтобы не бояться экспериментировать.

## Инструкция (пошагово)

1. Работайте в учебном проекте. Зафиксируйте исходное состояние файла (запомните содержимое или сделайте `git status` / коммит).
2. Попросите Claude внести заметную правку в файл и подтвердите её.
3. Откатите изменение одним из способов:
   - командой `/rewind` — выберите точку до правки (Claude Code сохраняет чекпойнты);
   - или просто попросите: «Отмени последнее изменение, верни файл к прежнему виду»;
   - или средствами git: `git checkout -- имя_файла` (если состояние было закоммичено).
4. Убедитесь, что файл вернулся к исходному состоянию.

## Критерий выполнения

Задача выполнена, если после отката содержимое файла совпадает с исходным, и вы попробовали минимум один способ отката.

## Подсказки

- `/rewind` откатывает к чекпойнту; какие именно состояния доступны — смотрите в списке, который показывает команда. Поведение чекпойнтов уточняйте в актуальной документации: этот механизм активно развивается.
- Самая надёжная страховка — git: коммит перед серией правок делает любой эксперимент обратимым. Подробнее — в модуле 6.

1. В сессии Claude Code нажмите `Shift+Tab` дважды (при пустой строке ввода): первое нажатие включает режим автопринятия, второе — plan mode. Смотрите на индикатор режима внизу экрана.
2. Если сочетание не сработало (бывает на Windows и в tmux) — есть запасные способы: команда `/plan` или запуск сессии сразу в этом режиме: `claude --permission-mode plan`.
3. Убедившись, что plan mode включён, дайте ту же задачу, что в 03-01: «Добавь в проект систему настроек пользователя».
4. Claude исследует проект и вернёт план: какие файлы затронет, в каком порядке, что учтёт. Файлы при этом не меняются — режим только для чтения.
5. Проверьте: `git status` должен показывать чистое дерево.
6. Пока **не** утверждайте план — читать и править его будем в следующих задачах. Выйдите из plan mode (`Shift+Tab`).

## Критерий выполнения

Задача выполнена, если вы получили структурированный план и убедились, что ни один файл не изменился.

## Подсказки

- Plan mode — это режим «только чтение» на уровне инструментов: Claude физически не может менять файлы, пока вы не одобрите план.
- Индикатор текущего режима отображается в строке состояния — привыкайте на него поглядывать.
- Сочетания клавиш и названия режимов могут отличаться в вашей версии — при расхождении ориентируйтесь на `/help`.

## Цель

Научиться читать план как ревьюер — находить в нём пробелы и неверные допущения до того, как написана первая строка кода.

## Инструкция (пошагово)

1. Включите plan mode и запросите план для задачи средней сложности в вашем учебном проекте (можно повторить задачу из 03-02).
2. Пройдите по плану с чек-листом ревьюера:
   - **Понимание**: правильно ли Claude понял, чего вы хотите? Первый пункт плана обычно выдаёт это.
   - **Полнота**: не пропущено ли что-то важное (обработка ошибок, крайние случаи, обновление связанных мест)?
   - **Излишки**: нет ли шагов, которые вы не просили (лишние библиотеки, «заодно отрефакторю»)?
   - **Допущения**: на чём план основан? Не додумал ли Claude требования, которые вы не озвучивали?
   - **Порядок**: логична ли последовательность шагов?
3. Выпишите (себе, на бумагу или в заметку) минимум один пункт, который требует уточнения или вызывает сомнение.
4. План пока не утверждайте — править его будем в следующей задаче.

## Критерий выполнения

Задача выполнена, если вы нашли в плане минимум один пункт для уточнения и можете объяснить, к какому пункту чек-листа он относится.

## Подсказки

- «План выглядит нормально» после беглого взгляда — самая частая ошибка ревью. Пробелы прячутся в том, чего в плане **нет**, а не в том, что есть.
- Смотрите на список затрагиваемых файлов: если там есть неожиданный файл — это вопрос; если нет ожидаемого — тоже вопрос.

## Цель

Научиться не соглашаться с планом: добиваться его изменения обычными сообщениями, пока план не станет вашим.

## Инструкция (пошагово)

1. Продолжите с планом из предыдущей задачи (или запросите новый в plan mode).
2. Внесите минимум две правки разного типа, отвечая Claude прямо в диалоге:
   - **Уберите шаг**: «Пункт про X не нужен, убери его из плана»;
   - **Добавьте требование**: «Добавь шаг: покрыть новую функцию простым тестом»;
   - **Ограничьте объём**: «Не трогай файл Y, реализуй без изменений в нём»;
   - **Поменяйте подход**: «Вместо новой зависимости используй то, что уже есть в проекте».
3. После каждой правки Claude вернёт обновлённый план — проверяйте, что правка учтена и не сломала остальное.
4. Добейтесь плана, под которым вы готовы «подписаться». Утверждать и выполнять будем в следующей задаче.

## Критерий выполнения

Задача выполнена, если итоговый план отличается от первоначального минимум двумя вашими правками, и вы готовы утвердить его без оговорок.

## Подсказки

- Править план — дёшево, править код — дорого. Каждая минута спора с планом экономит десять минут разбора неправильной реализации.
- Правки формулируйте как указания, а не вопросы: «убери X» работает надёжнее, чем «а точно ли нужен X?».

## Цель

Утвердить выверенный план и провести реализацию, сверяя её с шагами плана.

## Инструкция (пошагово)

1. Возьмите план, доведённый до ума в задаче 03-04.
2. Утвердите его: подтвердите предложение Claude перейти к выполнению (или выйдите из plan mode и скомандуйте «Приступай к реализации по плану»).

## Цель

Углубить навык чтения diff: в многошаговой реализации отклонить неудачное изменение и получить вариант лучше.

## Инструкция (пошагово)

1. Запустите через план небольшую задачу на 3–4 шага (например: «Добавь в проект простое логирование действий: модуль логгера + вызовы в двух местах»).
2. На каждом предлагаемом diff тренируйте быстрое чтение: что за файл, что добавляется, что удаляется, нет ли лишнего.
3. Минимум один diff **отклоните** — даже если он приемлем. Сформулируйте, что улучшить: «Отклоняю: назови функцию logAction вместо doLog и добавь параметр уровня логирования».
4. Сравните новый вариант diff с отклонённым.
5. Доведите задачу до конца.

## Критерий выполнения

Задача выполнена, если минимум один diff был отклонён с конкретной переформулировкой, новый вариант оказался лучше, и вся задача доведена до рабочего состояния.

## Подсказки

- Отклонить diff — не «обидеть» Claude и не сломать процесс: работа продолжится с учётом замечания. Кнопка «нет» — такой же рабочий инструмент, как «да».
- Отклоняя, всегда говорите **почему**: голое «нет» заставит Claude угадывать, что вам не понравилось.

## Цель

Пройти полный рабочий цикл: план → реализация → проверка → найденная проблема → исправление. Именно так выглядит реальная работа.

## Инструкция (пошагово)

1. Выберите маленькую, но **проверяемую** фичу — такую, результат которой можно запустить и увидеть (скрипт, команда, страница). Например: «Скрипт, который считает строки кода в проекте по типам файлов».
2. **План**: получите и отревьюйте план в plan mode (навыки 03-03, 03-04).
3. **Код**: утвердите и реализуйте (03-05).
4. **Проверка**: запустите результат. Проверьте не только «работает ли», но и крайний случай: пустая папка, файл в необычной кодировке, отсутствие аргументов.
5. Что-то не так? Отлично, это и был замысел. Опишите проблему Claude конкретно: что запустили, что ожидали, что получили (вставьте вывод ошибки).
6. Получите исправление, проверьте снова. Повторяйте, пока не заработает.
7. Если всё заработало с первого раза — усложните проверку из шага 4, пока не найдёте, что улучшить.

## Критерий выполнения

Задача выполнена, если пройден полный круг с минимум одной итерацией исправления: вы нашли проблему при проверке, сообщили о ней и получили работающее исправление.

## Подсказки

- Золотое правило сообщения о проблеме: **команда + ожидание + реальность + вывод ошибки целиком**. «Не работает» — худший баг-репорт в мире.
- Проверка руками — ваша часть цикла, её нельзя делегировать. Claude может написать код и даже тесты, но подтвердить «это то, что мне нужно» можете только вы.

## Инструкция (пошагово)

2. В plan mode попросите не просто план, а **поэтапный** план: «Разбей на 3–4 самостоятельных этапа так, чтобы после каждого этапа был работающий промежуточный результат».
3. Отревьюйте разбиение: действительно ли каждый этап даёт что-то работающее? Не тянет ли этап 1 за собой половину этапа 3?
4. Реализуйте **только этап 1** по полному циклу из 03-07 (план шага → код → проверка).
5. Остановитесь. Убедитесь, что промежуточный результат работает сам по себе.
6. Зафиксируйте оставшиеся этапы (в заметку или файл TODO.md) — они осознанно отложены, а не забыты.

## Критерий выполнения

Задача выполнена, если есть план из 3+ этапов с работающим результатом после каждого, этап 1 реализован и проверен, а остальные записаны и отложены.

## Подсказки

- Признак хорошего разбиения: каждый этап можно показать другому человеку. «Сделал половину базы данных» показать нельзя; «привычки добавляются и выводятся списком» — можно.
- Соблазн «дожать всё сегодня» — главный враг: большие непроверенные куски копят ошибки. Умение остановиться на работающем — это навык, и здесь он тренируется специально.
